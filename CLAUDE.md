# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

ARES 3 (NASA Space Apps 2026): a deterministic tick-based simulator of a crewed habitat (4 astronauts) that exports labelled multivariate time series (environment + vital signs, with fault ground truth) for an ML alert model, plus a React dashboard. Team: 2 software engineers (core/SDK/export), a bioengineer (Luca: vital signs, physiology) and a physicist (Mario: sensors, actuators, environment physics). The user writes in Italian; `docs/USO-DOCKER.md` and the GitHub issues are in Italian.

## Commands

```
uv sync --extra dev                                   # install (Python >= 3.11)
uv run pytest -q -n auto                             # tests in parallel (pytest-xdist): ~90 s on 16 cores, ~450 s serial; the floor is the longest test (a 14 h simulated day)
uv run pytest tests/test_engine.py::test_closed_system_conserves_every_species
uv run ruff check src tests
uv sync --extra serve && uv run ares3 serve scenarios/station/nominal.yaml --speed 10 --warmup-h 4   # live WebSocket bridge for the dashboard (ws://127.0.0.1:8765; protocol in src/ares3/serve/session.py; --warmup-h runs hours ahead so the ML is ready and the charts start full)
uv run python tools/demo_client.py --fault fire --module COL --seconds 60 --approve --ack   # a stand-in for the UI: injects a fault and prints mode / emergencies / requests / procedure steps
uv run ares3 validate scenarios/station/nominal.yaml  # loads scenario + builds every plugin, no run
uv run --with openpyxl python tools/build_station.py  # regenerate scenarios/station/* from Mario's workbook (--check: are they stale?)
uv run ares3 run scenarios/station/nominal.yaml --days 2 -o output/run1   # also --ticks N, --forever
docker compose run --rm ares3 run scenarios/nominal.yaml --days 1  # same CLI in Docker (scenarios/, src/, output/ are bind-mounted: no rebuild after edits)
uv run python tools/npc_report.py [--reuse]            # report for the bioengineer: HTML (figures as PNG) -> PDF via headless Chrome/Edge; normal day per NPC + 11 events (~10 min, needs --extra report)
uv run python tools/ml/make_dataset.py --nominal --randomize --medical --combos --seeds 1-3,5 --days 2 --features --out output/ml/feat   # ML feature rows (one process per run, `--resume` skips what is written)
uv run python tools/ml/train_anomaly.py && uv run python tools/ml/train_diagnoser.py   # -> models/station_v1/ (stage A and B), model cards next to them
uv run python tools/ml/check_monitor.py --nominal --seeds 5 --days 1                  # the real monitor on whole runs: false alarms and detection delays
cd dashboard && pnpm install && pnpm dev              # frontend, fully independent of the Python side
```

The small test habitat runs ~1,900x real time; the 16-volume station ~300x (3-4 ms per tick). There is no build step for the engine.

## Architecture

**The OFFICIAL station is `scenarios/station/` (Mario's ISS workbook -> `tools/build_station.py` -> generated YAML; read `docs/station.md`).** The old `hab/lab/greenhouse/airlock/lifeboat` habitat (`scenarios/base_layout.yaml`, `nominal.yaml`, `events/`, ...) is only the fixture of the engine tests and of Luca's physiology report. Station facts that are not obvious from one file: 14 ISS volumes + `lifeboat` (a Crew Dragon docked to NOD2, the return vehicle) + `eva`; gas moves between modules by PRESSURE difference (`gp_open/gp_closed` of a hatch, exact exponential relaxation in `World._bulk_flow`) and by concentration; IMV and cabin fans are actuators whose flow adds to the hatch exchange (`hatch.imv`); actuators publish TELEMETRY channels (`BaseActuator.telemetry`) that sensors with `target: actuator:<id>` observe, `station:<id>` sensors read the orbit/battery (`core/orbit.py`); `Tcs` is a lumped cold loop the CCAAs read; one CDRA is active (CDRA-B standby); playbooks isolate a module with `isolate:<module>`. New fault types: `actuator_degrade` (`fraction`, `ramp_s`, `component`), `actuator_stuck`, `hatch_stuck`, leak as `kg_day` / `steps` / `kpa_min`. Never edit the generated station files: change the tool.

**Package layering is enforced by `tests/test_architecture.py` (`LAYERS`)**: `schemas` imports nothing; `sdk` -> `schemas`; `core` and `plugins` -> `schemas`, `sdk`; `export` -> `core`. The only cross-imports below `core` are the leaves `core.constants/rng/clock`. A new package must be added to `LAYERS`. Plugin authors (Mario, Luca) must be able to work against `sdk` alone and never edit `core/`.

**One tick** (`core/engine.py`, phases are documented in the module docstring and order matters): faults active -> NPC schedule/MET -> crew exchange and physical faults applied to the world -> actuators (use the previous tick's snapshot, sensed readings and the agent's commands from the previous tick) -> world physics (hatch diffusion, heat, condensation) -> snapshot -> physiology -> sensors + sensor faults -> alarms, agent decides. The agent's commands take effect one tick later to avoid circular dependencies.

**Truth vs. measurement is a core rule.** `ModuleState`/`NPCState.vitals` are ground truth. Sensors return an `Observation` with `value` (noisy, lagged, fault-corrupted) and `value_true`; controllers and the agent read `ctx.reading(sensor_id)`, never the true state. Alarm rules evaluate the true state. Sensor faults (bias/drift/stuck/dropout/noise) are applied by the engine on top of the sensor's output; a sensor must model only the healthy device.

**Plugins return effects, they never mutate the world.** `BaseSensor.step -> Observation`, `BaseActuator.step -> list[ModuleFlow]` (rates in mol/s and W, so dt-independent), `PhysiologyModel.step -> VitalsUpdate`. The core applies them and books every mole in `World.ledger`; `tests/test_engine.py` checks conservation of O2/CO2/N2/H2O in a closed system.

**Monitoring system and emergency response** (ISS-like, never Mars: see NASA SpaceOps 2023 on ISS emergency ops). `monitor:` in a scenario (`scenarios/monitor_placeholder.yaml`) = detectors -> classifier -> playbooks -> `crew_response`. Detectors (`plugins/monitor/`, subclass `BaseDetector`) read SENSED observations of a *metric on modules*, never sensor ids; `core/monitor.py` debounces them into `Emergency` (suspected/confirmed/cleared) in `SimulationTick.emergencies`; `core/responder.py` runs the playbook (`auto` steps at once, `confirm` steps become `PendingAction`s that ANY crew member or the UI can approve, `on_timeout: execute|discard`) and enforces the ISS rule that no hatch is closed on someone cut off from a return vehicle; `core/response.py` makes the NPCs react (Warn/Gather/Work, roles and succession by crew profile, evacuation to the `return_vehicle` module `lifeboat` when TRes is low). Commands take effect one tick later. `sdk/control.py::ControlAPI` is the only inbound surface for the UI (`Engine.inject/stop_event/approve_action/reject_action/declare_emergency`); `ares3 serve` (`src/ares3/serve/`, `Session` + WebSocket server) streams ticks and takes `ControlAPI` commands as JSON; the dashboard side is `dashboard/src/telemetry/websocket.ts` (`WebSocketBackend`, a `VitalsSource` plus command client) and the hand-kept mirror in `types.ts`; the UI components themselves are another developer's. Loss of cabin air is graded like the ISS does (`docs/reference/depressurization-sources.md`, NASA ICES-2025-126): `PressureDrop` detectors per time scale (30 s breach, 300 s rapid >= 0.87 mmHg/min, 30 min fast >= 0.4, 2 h and 6 h slow/trend; the P probe's noise sets the windows, re-check the thresholds if Mario changes it) plus a 490 mmHg floor detector, TRes = `P ln(P/Pmin)/|dP/dt|`. Playbooks have a `severity`: critical (rapid) stops gas introduction, fans off, isolates the module and the crew retreats (TRes <= 10 min -> `lifeboat`, whose hatches are CLOSED once everyone is aboard: `crew_sealed`); a warning (fast/slow leak) raises no group alarm, keeps the make-up gas on, and the engineer patches the leak after `repair_leak_s` (fault param `repairable: false` opts out; `Monitor.forget` then drops the module's detector history). Fire is a physical fault (`type: fire`, `Engine._fire`): heat, O2 consumed, CO2, CO and smoke (contaminants live per module in `World`, not as gas species); it weakens with the fans off, below ~12 kPa pO2, and when its fuel runs out; the playbook turns ventilation and gas introduction off and the crew discharges the extinguisher. If the extinguisher is discharged and the fire still burns `fire_evacuate_s` later (fault param `extinguishable: false` to test it) everyone evacuates to the `lifeboat` and returns after the all-clear; the engineer (role `systems`) goes to a module with a confirmed `equipment` emergency and, after `repair_s`, brings its offline actuators back. Carbon monoxide poisons the crew: `plugins/physiology/toxicity.py` (Coburn-Forster-Kane COHb, sources `docs/reference/toxicology-sources.md`) is called from `HumanModel`; COHb lowers the FUNCTIONAL oxygen saturation (hypoxia dose, health state, tachycardia), while the `spo2` vital (pulse oximeter) does not see it: the SpCO channel is `cohb_pct`. `co_source` fault releases CO. The monitor watches crew wearables (`NpcThreshold`, targets `all_npcs`) and opens a `medical` emergency with a `subject` and a `cause` inferred from which detector fired (YAML order = specificity: SpCO before SpO2), and the medic goes to the flagged crew member even without a group alarm. FED (ISO 13571) and HCN/NH3 toxicity are not modelled. Test emergencies on the station profile (`scenarios/events/debug_station.yaml`, fixture `station`, the small habitat) for unit tests; the full ISS station for integration (`tests/test_station.py`).

**Three states, ML recognition and crew procedures** (plan in `piano.md`, sources `docs/reference/monitoring-ml-sources.md`, UI contract `docs/monitor-ui.md`). `SimulationTick.monitor_mode` is `passive` / `alert` / `reaction`: the maximum over the open emergencies, up at once, down after `classifier.mode_hold_s`; `Emergency.alert_class` (emergency / warning / caution / advisory, from `classifier.classes`) is what the UI colours by. Besides the rule detectors there are two ML stages in `plugins/monitor/ml/` (imports only `sdk`/`schemas` + numpy/sklearn; training lives in `tools/ml/`, never in the package), both fed by the SAME `features.py::FeatureExtractor` (online in the detector, offline in `make_dataset.py --features`: no training/inference gap; levels are not features, since every sensor unit has its own fixed error per seed): stage A `AnomalyDetector` = one PCA (T2 + SPE) per subsystem (`tools/ml/groups.yaml`), trained on NOMINAL days only, emits `anomaly` (class caution, no playbook -> ALERT); stage B `DiagnosisDetector` = one gradient-boosting classifier per family (physical / actuator / sensor / medical) that names the fault in `Signal.cause`, with the explanation in `Emergency.evidence`; the `diagnosis:` table of the monitor config (generated from `tools/ml/classes.yaml`, the one label -> emergency mapping) says what it opens. The ML detectors are listed LAST (a rule that names a cause wins) and never replace a rule. `models/station_v1/*.joblib` are committed (joblib runs code on load: only ours). Rule detectors that double as features: `Variance` (stuck / noisy sensor against its own baseline, on the differences), `RedundancyResidual` (redundant sensors that stop agreeing, vs their own baseline offset), `EarlyWarningScore` (NEWS2-like on the 5-minute mean, HR/RR not scored during and 30 min after exercise). `classifier.group_by: connected` fuses the leak signals of modules joined by open hatches into the module that falls fastest. Crew **procedures** (`core/procedures.py::ProcedureRunner`, YAML `procedures:`) are the checklist for the people next to the playbook (the safing of the machine): steps `instruction` / `action` / `check` (on SENSED values) / `question` / `escalate`, state in `tick.procedures`, closed by `ControlAPI.ack_step` or by the NPC of the step's role (`crew_response.npc_follows_procedures`). New actions: `power` (cut / restore a module's supply: the fire playbook cuts it, vital modules USL / NOD3 only after a confirm that runs on timeout; restoring is only PROPOSED, the guard never cuts the lifeboat or the EVA volume) and `sensor substitute` (control loops read a redundant sensor; `substitutes:` generated from the workbook). The dataset side: `scenarios/station/fault_ranges.yaml` (generated: sheet 06 min/max) drives `make_dataset.py --randomize`; the label is "fault active", the visible-effect time comes from the TWIN run (same seed without the fault: identical until the fault acts). ML numbers are simulation time on synthetic data, never flight performance.

**Everything is configured in YAML (`scenarios/`), validated by Pydantic (`schemas/`).** A plugin is referenced as `package.module:Class` (importable, no registration). A scenario file = environment profile + layout + crew + faults + seed. Details that are not obvious from one file:
- `layout:` can be a list of files, merged in order (modules/sensors/actuators are separate files). Sensors can be written as `sensor_sets` rules (expanded in `load_scenario`), so 30 or 120 sensors cost the same; default id is `{target}_{metric}` (case-sensitive: `hab_ppCO2`). Actuators and faults reference sensors **by id**, so changing the sensor set requires updating them.
- The environment (Mars / orbit) is a swappable profile (`scenarios/environments/`): gravity, `day_length_s`, atmosphere, exterior temperature and the alarm rules (NASA-STD-3001). Actuator setpoints left unset default to the environment's nominal values. Module microclimates (`atmosphere:` in a module) are partial overrides, never absolute values. `environment_overrides` in a scenario deep-merges over the profile.
- Time of day comes from `SimClock` using the profile's day length (a Mars sol is 88775.244 s); schedules are in local hours 0-24.
- Determinism: one root `seed`; every component gets `core/rng.derive(seed, kind, id)`, so adding a sensor does not change other components' random streams.
- Anomaly labels (`core/faults.py::label_row`, `Engine._row`): a row is anomalous when a fault targets the sensor, the thing measured, its module, or an actuator of that module. It means "fault active", not "effect visible". Highest `priority` wins `anomaly_type`; all ids go to `anomaly_ids`; non-anomalous rows are `nominal`.
- Export (`export/writers.py`) writes one Parquet/CSV part per simulated `chunk_hours` (long and wide), so unbounded runs use bounded memory.

## Conventions and gotchas

- Mario's station (`scenarios/station/`) is the OFFICIAL layout/sensors/actuators/fault catalog; what it leaves out is ours and listed in `docs/station.md` (ESTIMATE, to confirm with him: generation 140 kW, CDRA eta 0.85, rack heat, the lifeboat). Other files are marked `PLACEHOLDER - awaiting review by Mario/Luca` (small habitat, physiology, crew, monitor). They exist to make the pipeline run; do not present them as validated. Keep the replaceable-pieces design: don't hard-wire anything to the example layout (tests do depend on the `hab` and `lab` module ids).
- Every physical constant needs a source tag (`[S1]..[S20]`, see `docs/reference/ambientmonitor/verifica-dati.md`) or the word ESTIMATE. `docs/reference/ambientmonitor/` documents the author's earlier JS simulator that the metabolism table, alarm limits and sensor noise defaults were ported from; don't reintroduce its 2.5D CFD (too slow, and ruled out by design).
- NPCs: the 4 members of `scenarios/crew.yaml` ARE Luca's ASTRO_01..04 (`alias`; mapping cmd/bot/eng/med is our proposal, to confirm). Physiology is `HumanModel` (`plugins/physiology/human.py`, on top of `ProfileModel` -> `BaselineModel`; sources [P1]-[P22] in `docs/reference/physiology-sources.md`; unsourced numbers say ESTIMATE). It keeps a health state (0 ok .. 3 unconscious, 4 dead; death is optional: `death_enabled`, set per scenario with `physiology_overrides:`) driven by a dose of hypoxia/CO2/heat, per-person parameters from sex/age/mass (`age_y`, `height_cm` in `crew.yaml`, our estimates), circadian rhythm and sleep stages, core temperature, hydration, microgravity adaptation and a beat-to-beat RR series. The vital `gas_scale` (0 dead, resting if unconscious) is read by the engine to scale the NPC's gas exchange. Reactive NPC behaviour is out of scope (the project monitors health). Event scenarios and the report's nominal day (`scenarios/events/day_nominal.yaml`) run in Luca's STATION atmosphere (orbital_station profile, 758 mmHg, 21 % O2): all his notebooks assume sea-level/ISS air; `nominal.yaml` and `events/day_mars.yaml` stay on Mars for comparison. The launch phase from Earth that Luca's notebooks consider is NOT simulated. The EVA volume uses 42 % O2 (our assumption, Luca's 28 % gives PIO2 85 mmHg). Event scenarios live in `scenarios/events/` (faults of category `medical` carry the episode params). A module with `alarm_mode: occupied` (the `eva` volume) only alarms while someone is inside.
- YAML 1.1 reads a bare `on:` key as boolean `true`; avoid `on`, `yes`, `no` as keys.
- Units: SI except partial pressures in kPa, ppCO2 and PIO2 in mmHg, temperatures in degC. The NASA oxygen limits are on PIO2 (not cabin pO2).
- `dashboard/` is a standalone Vite/React app. `dashboard/src/telemetry/types.ts` mirrors `sdk/types.py` by hand (Python is the source of truth); `VitalsAdapter`/`VitalsSource` are interfaces only. `dashboard/src/data/anatomy.json` is GPL-2 derived (gganatogram); keep `dashboard/LICENSE` and `THIRD_PARTY_NOTICES.md` with it.
- Git: commit messages and PR descriptions carry no attribution lines (`.claude/settings.json` disables them). Open issues for Mario are on GitHub (#1-#6).
